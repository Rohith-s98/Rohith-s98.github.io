01 · How I think

Four habits I bring to every problem

01

Start from failure

Before "does it work?", I ask "how does it break?" I map the risks first and test the riskiest path first, because users won't take the happy path.

02

Make the invisible measurable

A system you can't see is a system you can't trust. SQL reconciliation, Datadog dashboards and alerts turn "seems fine" into evidence.

03

Automate the repeatable, think about the rest

Frameworks exist so people can spend their time on judgment. I build automation to be reused and maintained, not admired once.

04

Trust, but verify (AI included)

Exact inputs, explicit guardrails, human review. I apply the same discipline to AI tools as to any system under test.

Infosys · Migration testing

Proving a migrated system behaves exactly like the old one
Problem
A legacy on-premise web application was moving to Microsoft Azure under compliance requirements. "It deploys" isn't the same as "it behaves the same", and differences hide in both the UI and the database.
Approach
Ran the legacy and migrated web apps side by side with one-to-one tests, so every flow had a baseline to compare against. On the database side, checked tables column by column and verified the stored procedures ran correctly after the move. Test plans and sign-off reports made release readiness explicit.
Outcome
The migration was validated layer by layer, app and database, against the system it replaced.
Quintet · Automation

From manual regression to a framework the team reuses
Problem
A client SaaS platform (work orders, service requests, scheduling) where regression testing leaned heavily on manual effort and feedback came late.
Approach
Built and maintain an end-to-end framework in Playwright and TypeScript using the Page Object Model for reusable components. Wired suites into CI/CD on GitHub, and covered APIs across integrated microservices with Postman and Playwright.
Outcome
Faster feedback on every change and less manual regression effort, on a codebase built to be maintained.
Quintet · Observability

Seeing failures before users do
Problem
Automation failures in staging and production are only useful if someone can tell a real defect from noise, quickly.
Approach
Configured targeted Datadog dashboards and alerts to watch application health and debug failing scripts, and led QA for major releases: test strategy, test plans and UAT with product and engineering.
Outcome
Release decisions backed by signals, not guesswork.
Personal · AI + automation

An AI-built pipeline, tested like any other system
Problem
Job searching is repetitive and error-prone. Could an AI coding agent automate it without making things up?
Approach
I wrote the requirements and rules; Claude Code wrote the code. The result is a scheduled Node.js + PowerShell pipeline that pulls roles from public job APIs (Greenhouse, Lever, Ashby), scores them, and generates tailored documents and a local dashboard. Then I tested it like a system under test.
Outcome
Caught it matching the wrong job (exact matching fixed it), overstating claims (now a source-of-truth rule with a review step), and paraphrasing inputs (switched to exact text from official APIs). The lesson: AI is fast, and guardrails are what make it trustworthy.
